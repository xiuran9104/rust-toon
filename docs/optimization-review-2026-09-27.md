# 项目优化排查记录（2026-09-27）

审阅基线：`877329d41c082276a55e6b7d4dc115203f87bd53`（`main`）。已执行 `git fetch origin`，本地与 `origin/main` 提交差异为 `0 / 0`，无需合并。审阅前工作区干净。

本次对 Gateway、框架层、System/Infra/AI/Toonflow/Media、Worker、数据库迁移、前端和 CI/部署入口进行了静态扫描，并深入检查下面列出的调用链。结论不是全量运行验收，也没有进行生产压测；性能收益需用实际数据验证。本次仅新增本报告。

## 已有基础

- 分布式媒体任务已经有 PostgreSQL outbox、JetStream、lease/heartbeat/fencing 以及 Worker 排空流程，可在现有实现上改进。
- Gateway 保持单副本，Kubernetes 使用 `Recreate`；当前 Agent/Workflow 的进程内运行状态仍不支持多 Gateway 协调。
- Toonflow 媒体读取已经使用 `Body::from_stream` 并传递 Range；不能把 Infra 文件读取的问题归因于全部媒体接口。
- 新版 Agent 历史已经分页，默认 24 条、上限 50 条；普通 AI 聊天及旧版 Agent 历史仍有不同实现。
- 生产工作台的 `loadFlow` 已有请求合并和目标项目/剧本检查；剩余问题主要是每轮请求数量。
- CI 已包括 Rust、前端、数据库迁移、媒体任务、部署及备份等检查。需要补的是具体边界和发布入口的一致性。

## 优化清单

### 01 · P0：审计日志保存了未脱敏的凭据

**证据**：`services/gateway/src/audit.rs:121` 保存包含查询参数的 URL；`:151` 保存请求 URI 和头；`:217` 遍历全部头，没有排除 Authorization、Cookie 或 Set-Cookie；`:130`、`:160` 捕获请求与响应正文。`:271` 的测试甚至明确要求保留示例 WebSocket token。

**影响**：登录请求的密码、登录响应的令牌、普通请求的 Bearer token、媒体/WS URL 中的 token，以及模型配置正文中的密钥都可能进入 `infra_api_access_log`。日志读取和备份因此扩大了凭据的可见范围。

**实施建议**：统一处理头、查询参数、JSON/表单中的敏感字段；认证及密钥管理接口按白名单记录元信息；其他正文仅记录必要摘要。先完成字段脱敏，再截断展示长度，避免截断后 JSON 无法解析导致原文回落。修改当前保留 token 的测试预期。

**验收**：以虚构凭据覆盖登录、刷新、模型配置、WS、媒体读取；检查数据库日志及错误路径均无原值。已有日志的处置应单独评估，避免直接删除审计数据。

### 02 · P0：Agent 授权与令牌撤销校验不一致

**证据**：`crates/modules/system-server/src/database_auth.rs:32` 只处理 Authorization 请求头。`crates/modules/toon-server/src/toonflow_ws.rs:348` 仅验证 query token 的 JWT，`:371` 接收后不使用用户身份，`:698` 直接替换客户端提交的项目、剧本与隔离键。历史查询按隔离键取数据；`toonflow_agents.rs:1141` 的运行入口没有用户参数，`:176` 按项目 ID 读取上下文。

HTTP Agent 入口也需一起处理：`toonflow_agents.rs:1337` 的 `start` 仅检查功能权限，`run_state`、`stop` 等按运行 ID 操作，未复用项目归属校验。仓库已有可复用的 `toonflow_episode_renders.rs:117`（项目归属）及 `:139`（剧本归属）校验。`toonflow_storage.rs:1024` 的媒体 query token 同样直接使用 JWT 内的用户权限。

**影响**：WS 新连接不能及时拒绝已撤销令牌或已禁用账号；Agent 请求中的资源 ID/隔离键缺少与当前用户的绑定，存在越权读取历史或执行操作的路径。媒体权限变更也可能滞后至 JWT 过期。

**实施建议**：提取共用的有效会话校验，统一加载当前用户权限；在 WS 握手、上下文切换、历史读取、Agent 启停及工具执行前校验项目和剧本。隔离键由已授权的上下文生成或严格验证。明确长连接期间撤权的生效策略。

**验收**：两个普通用户的项目相互隔离；不具备功能权限的用户无法执行 Agent；撤销 token、禁用账号、移除权限后，HTTP、WS 新握手及媒体访问行为一致；切换上下文不能绕过校验。

### 03 · P0：知识库 URL 下载缺少目标与资源限制

**证据**：`crates/modules/ai-server/src/knowledge.rs:215`、`:453` 将用户提供的 URL 直接交给 `reqwest::get(...).text()`。分段预览 `s_split` 只要求登录，未增加知识库权限检查；这两条下载路径没有显式的目标地址策略、响应大小限制或专用超时配置。

**影响**：登录用户可让 Gateway 请求其网络可达的地址，形成 SSRF 风险；大响应或缓慢响应也会占用网关资源。

**实施建议**：优先通过受控的已上传文件标识读取。确需远程 URL 时，统一下载组件，校验协议、域名与解析地址，对每次重定向重新检查，设置连接/整体超时、最大读取字节数及并发额度。合法的内部对象存储地址通过明确配置允许。

**验收**：使用本地模拟服务验证回环/私网目标策略、重定向、大文件、慢响应和中途断流；正常受控存储读取保持可用。

### 04 · P1：审计正文限制未限制实际读取，写入也缺少背压

**证据**：`services/gateway/src/audit.rs:139`、`:170` 调用 `to_bytes(body, usize::MAX)`。512 KiB 限制主要依赖 Content-Length 预判和读取完成后的展示截断；缺少 Content-Length 的可捕获请求会先完整缓冲。`:82` 每个请求都 `tokio::spawn` 写日志，`:91` 忽略写入错误。

**影响**：请求在进入业务提取器的大小校验前可能已经被审计层完整读取；大响应延迟返回并放大内存占用。数据库变慢时，大量日志任务与业务请求竞争同一连接池，失败也不易观察。

**实施建议**：业务大小限制放在读取前生效；审计使用受限的流式预览，超限停止记录而不截断业务正文。写日志使用有界队列、批量写入和明确的满队列策略，暴露丢弃/失败/积压指标，并在停机时排空。复用认证阶段已得到的数据库用户 ID，减少每条日志额外的用户查找。

**验收**：无 Content-Length 的大请求、大 JSON 响应、慢数据库下，内存和日志待处理量均受控；审计不会破坏业务正文，失败可观测。

### 05 · P1：限流 IP 信任边界与代理配置不匹配

**证据**：`crates/framework/redis/src/rate_limit.rs` 的 `client_key` 无条件取 X-Forwarded-For 第一项；`deploy/nginx/distributed.conf` 使用 `$proxy_add_x_forwarded_for` 保留并追加来访头。

**影响**：在该部署路径下，来访者能控制头部第一项，使同一来源请求使用不同限流键。按原始 URL 路径限流也会为不同资源 ID 创建不同桶。

**实施建议**：统一可信代理策略：边缘覆盖不可信来源头，应用仅对可信代理解析转发链。登录及昂贵操作配置独立额度；动态资源路由使用路由模板或业务操作名。保留现有账号失败锁定机制。

**验收**：改变自报 X-Forwarded-For 或资源 ID，不能绕过同一操作额度；真实代理链及共享出口用户的行为符合预期。

### 06 · P1：Worker 并发上限实际按任务类型分别计算

**证据**：`services/toon-worker/src/main.rs:270` 为每个 Handler 启动 consumer；`:597` 在每个 consumer 内创建独立的 `Semaphore(settings.concurrency)`。默认注册视频质检、视频导出和定时任务三个 Handler。`docs/configuration.md:172` 却将其定义为单实例总并发上限。

**影响**：配置为 4 时，三类任务都有积压的情况下，代码允许合计最多 12 个 Handler 同时执行；其中视频导出和质检合计可达 8 个。实际受各任务和其他限制影响，但单实例总上限并不是文档描述的 4，容易低估 CPU、内存及临时盘压力。

**实施建议**：在 Worker 启动时创建共享总信号量，再按需要叠加各类任务额度。注册信息、指标、配置文档以及停机排空逻辑使用一致语义。

**验收**：混合三种 mock 任务，记录同时执行数，确认总数不超过配置值；某类长任务不应永久饿死其他类别；停机仍能排空。

### 07 · P1：WebSocket 出站队列无界

**证据**：`crates/modules/toon-server/src/toonflow_ws.rs:377` 使用 `unbounded_channel`；发送端同步入队，转发端逐条等待 socket 发送，未对出站积压设置上限。旧版历史路径也会全量加载并入队。

**影响**：生产消息速度持续高于客户端接收速度时，单个连接的内存随积压增长；并发慢连接会放大影响。

**实施建议**：使用有界队列，合并高频文本 delta；定义发送超时、队列满时的连接关闭/任务取消语义，避免静默丢失完成和错误事件。历史统一分页，并监控连接数及队列深度。

**验收**：模拟暂停读取的客户端，检查内存上限、超时回收、事件完整性和重连后的历史恢复。

### 08 · P1：运行事件重复轮询，关闭后仍有请求

**证据**：`apps/web/apps/web-antd/src/views/toonflow/settings/index.vue:246` 每 3 秒刷新；同一页面使用的 `components/AgentRunEventDrawer.vue:26` 每 2 秒 emit refresh。父页面的关闭处理仅设置 `eventOpen = false`，只在卸载时清理其 timer；`refreshRunEvents` 也没有请求互斥、运行 ID 版本检查和事件 ID 去重。

**影响**：运行中同一抽屉同时被两个定时器刷新，关闭后父页面继续请求。慢请求可能使用相同游标，重复追加事件；快速切换运行时，旧响应可能写入新运行的列表。页面没有刷新 `selectedRun.state`，终态也不能可靠停止轮询。

**实施建议**：由一处统一管理轮询；上次请求完成后再调度下一次。关闭、页面失活、组件销毁和任务终态时停止；返回时检查 runId/请求版本，按事件 ID 去重，并同步任务状态。

**验收**：fake timers + 延迟 Promise 覆盖单次请求、关闭、KeepAlive 失活、切换运行、乱序响应、任务完成。

### 09 · P1：生产工作台每轮按节点逐个查询状态

**证据**：`apps/web/apps/web-antd/src/views/toonflow/projects/detail/useProjectDetail.ts:455` 先发三个请求，再在 `:480` 对每个节点调用 `getLatestWorkflowNodeRun`；`:1039` 在 Agent 活动时每 1.8 秒触发刷新。`crates/modules/toon-server/src/toonflow_workflow_control.rs:129` 每次请求还执行权限/归属校验和陈旧节点恢复。

**影响**：N 个节点每轮至少产生 `3 + N` 次业务请求，另有其他状态轮询；并行发送缩短等待，却没有减少请求、认证、SQL 和日志数量。现有 `loadFlow` 已合并重叠请求，应保留。

**实施建议**：增加按项目/剧本一次返回所有节点最新状态的批量接口，必要时合并工作台快照；只读取界面需要的状态，详情按需取。陈旧节点恢复集中调度，避免每个节点读取都触发全局维护逻辑。

**验收**：相同节点规模下，每轮状态查询变为一次；切换剧本仍不会显示旧数据；比较请求数、SQL 次数、传输量及 p95 响应时间。

### 10 · P1：普通 AI 聊天全量历史和切换响应竞争

**证据**：`crates/modules/ai-server/src/chat.rs:241` 对一个会话 `fetch_all`，没有历史页大小限制。`apps/web/apps/web-antd/src/views/ai/chat/index/index.vue:161` 的 `getMessageList` 将 await 结果直接赋给当前消息列表，没有在返回时检查会话 ID 或请求序号。

**影响**：长会话的传输、序列化和页面渲染持续增加；快速切换会话时，较慢的旧请求可能覆盖新会话内容。

**实施建议**：增加以消息 ID 为游标的历史分页，向上滚动加载；为请求绑定会话 ID/版本并取消或忽略旧响应。数据量确有需要时再引入虚拟列表。保持当前基于用户的会话归属校验。

**验收**：长会话单页返回有明确上限；A→B 切换时延迟 A 的响应，界面始终显示 B；加载旧页不跳动、不重复消息。

### 11 · P1：知识库检索全量传输向量并在 Gateway 排序

**证据**：`crates/modules/ai-server/src/knowledge.rs:487` 对每个知识库分别请求查询向量；`:511` 获取全部有效片段及 embedding，在 Rust 中计算余弦相似度、完整排序后截取 top-K。`s_search` 也使用全量读取。

**影响**：检索计算与向量传输至少随片段数量和向量维度线性增长；多个知识库使用相同模型时，查询 embedding 仍重复请求。达到阈值的候选在截取前就构建 JSON，也增加分配。

**实施建议**：先按模型复用同一次查询的 embedding、减少返回字段及中间 JSON，使用有界候选集合。数据规模增大后，评估数据库侧向量 top-K 与索引方案，保留文档状态和资源授权过滤。数据库变更必须新增迁移并完成仓库规定的空库验证、快照与断言更新。

**验收**：用固定相关性样本对照召回结果，再比较不同片段规模下的检索 p95、Gateway 内存、数据库返回字节数与 embedding 调用次数。

### 12 · P1：知识库导入可能留下不完整文档

**证据**：`crates/modules/ai-server/src/knowledge.rs:200` 在 HTTP 请求中逐文档执行下载、插入文档、获取 embedding、逐条插入片段；这些写入没有作为一个完整发布事务。`:234` 直接 `zip(parts, embeddings)`；`provider.rs:854` 的 embedding 解析也未校验返回条数、输入 index 对齐和统一维度。

**影响**：供应商失败或中间某次插入失败会保留部分数据；返回向量数量少于片段时，zip 会少写片段但流程仍可返回成功。返回顺序不同还可能绑定错误文本。

**实施建议**：引入导入状态和可重试任务；网络调用在数据库事务外完成，先校验向量数量、index 与维度，再批量写入并原子发布完成状态。分批处理大文档，以幂等标识防止重试重复建档。

**验收**：模拟少返回、乱序返回、错误维度、供应商超时和中途数据库失败；均不应报告完整成功，重试后片段应完整且无重复。

### 13 · P2：密码校验和 Excel 生成占用异步执行线程

**证据**：`crates/modules/system-server/src/application.rs:40` 在 async 登录函数中直接执行 bcrypt/Argon2 校验；`crates/modules/infra-server/src/excel.rs:38` 直接执行同步 workbook 构建，`:210` 将工作簿压缩到 buffer。用户管理也有同步密码散列调用。

**影响**：这些 CPU 操作没有 await，持续占用当前 Tokio 执行线程；高并发登录或导出时，可能影响其他请求的调度。实际影响需测量。

**实施建议**：将密码散列、校验和中等规模 Excel 构建放到受限的阻塞任务池，搭配额度控制；超大导出使用后台任务。保留账号锁定的并发保护，避免将整个数据库事务搬入阻塞线程。

**验收**：并发登录/导出期间测量普通读取接口延迟，同时确认锁定、权限与导出内容保持正确。

### 14 · P2：Infra 下载全量缓冲，上传有重复复制和请求

**证据**：`crates/modules/infra-server/src/object_storage.rs:116` 读取完整对象为 Vec；`lib.rs:808` 等待全部下载后构造响应。上传 `lib.rs:775` 克隆完整文件字节；`object_storage.rs:104` 每次 put 都先请求创建 bucket。上传已有默认 20 MiB、可配置至 100 MiB 的限制，问题是复制、并发内存和首字节等待。

**实施建议**：复用 Toonflow 已有的流式读取和 Range 思路，统一对象存储客户端；避免不必要的完整字节复制，bucket 初始化移到启动/明确的初始化路径。保留下载的 Content-Disposition、CSP 和 nosniff 保护。

**验收**：比较受限大文件的首字节时间和多路下载内存；核对 Range、错误状态及下载响应头。

### 15 · P1：手动发布入口未要求目标提交通过 CI

**证据**：`.github/workflows/delivery.yml:32` 对 `workflow_dispatch` 直接放行发布；随后选择当前 `github.sha` 构建镜像，deploy 仅依赖 publish。自动入口检查了 CI success，手动入口没有同等的目标提交校验。

**影响**：从工作流文件本身看，手动发布可进入没有对应成功 CI 的提交。GitHub Environment 的外部保护配置本次未读取，不能据此断言生产实际无审批。

**实施建议**：发布前校验目标 SHA 对应的必需检查，或让手动发布复用同一验证工作流；优先提升已经验证的不可变镜像 digest。保留 Environment 保护和镜像签名。

**验收**：未验证/检查失败的 SHA 被拒绝；检查通过的 SHA 才可发布，产物来源和实际部署 digest 一致。

## 后续维护项

- **格式与工具链**：当前 `cargo fmt --all -- --check` 失败，共 15 个文件存在格式差异。先统一格式基线与工具链版本，避免格式门禁遮住真正的 lint/test 结果。该结果不等于代码编译失败。
- **认证查询**：`system-server/src/infrastructure.rs:51` 使用计算出的 UUID 表达式查用户；当前迁移未见该表达式索引。先用有代表性用户量的 `EXPLAIN (ANALYZE, BUFFERS)` 验证，优先复用已查到的数字用户 ID，再决定是否新增索引。不要通过长期缓存有效 token 来牺牲撤销即时性。
