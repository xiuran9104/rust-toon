## 结论

保留 Rust 后端、Vben 前端和现有业务数据，以 Toonflow-app 的 Agent 分工、专业内容模板、按需衍生与工作台交互作为功能基线。当前已具备两套 Agent 和主要执行阶段，重点是修通上下文与技能传递、统一相互冲突的规则、补齐执行过程反馈，而非重新实现一套 Agent。

先完成主剧场对齐，再增加专题剧场入口。古今混合应先在现有项目生效，新入口复用项目、角色身份、资产、分镜、轨道与任务服务。不要要求用户重建项目或重复填写简介。

## Agent 工作方式对比

| 维度 | Toonflow-app 基线 | Rust 当前实现 | 处理建议 |
| --- | --- | --- | --- |
| 剧本 Agent | 决策 → 骨架/改编/剧本执行 → 编辑审核 | 对应子 Agent、独立模型键、工具循环、保存接口均存在 | 保留结构；逐项核验实际产出与保存结果，不能按接口同名判定已对齐 |
| 生产 Agent | 决策 → 导演规划、衍生分析、衍生生成、分镜表、面板、分镜图 → 监制 | 阶段均存在，另有视频提示词及编辑工具；部分工具直接暴露给决策层 | 对齐职责边界；决策层委派任务，执行层持有本阶段写工具，监督层只读 |
| 动态技能 | 按选定画风和导演手册扫描目录，执行层获得技能目录及 `activate_skill` | `dynamic_skills` 只判断画风/手册是否非空，再放行整个 `art_skills/`、`story_skills/`；执行层未复用完整技能目录注入 | **P0**：按选定路径精确筛选，统一技能目录、加载接口与执行层上下文 |
| 技能内容存储 | 技法 Markdown 与运行时加载目录一致 | 同步脚本把画风/导演技法存进 `creative_manuals`，动态加载查询 `skill_list`；现有同步脚本没有把这类目录完整注册为动态技能 | **P0**：提供统一解析器，将手册条目映射为可加载技能；读取运行库确认实际缺口 |
| 项目上下文 | ScriptAgent 明确携带简介；生产执行层注入画风/叙事技能和模型信息 | 剧本父/子 Agent 与生产子 Agent带简介；生产决策层读取简介和画风却没有输出到生产上下文；资产提取输入也未显式带简介 | **P0**：统一上下文构建，所有阶段共享项目世界观、当前集/场、模型能力及引用资产 |
| 实时工作区 | 多个生产工具通过 Socket 向前端请求数据/执行写入 | 服务端从业务表读取剧本和资产，工作区保存规划内容 | 保留服务端数据来源；对齐前端实时刷新，避免依赖页面常驻才能运行 |
| 执行过程展示 | 子 Agent 独立消息，逐块消费流式输出，工具有过程消息 | 决策层有流式输出；剧本子 Agent 最后整体回填；生产执行循环使用非流式调用，内部请求 `emitter: None` | **P1**：贯通父子运行事件，展示当前阶段、工具结果、产出与失败位置，无需展示内部推理 |
| 记忆 | 近期消息、摘要、向量召回、深度检索；本地 ONNX | 同类能力已有，使用配置的 embedding 模型；普通相关记忆只搜索最近100条，失败可降级词项匹配 | 保留可配置模型；增加模型/维度版本、项目隔离和长历史召回验收，后续按需提供本地模型 |
| 失败恢复 | AbortSignal 与阶段重新派发 | 运行/工具记录、失败原因、重试关联已有；`retry` 重新提交原始请求；活跃 Agent 注册表仍在 Gateway 内存中 | 保留记录；补阶段检查点和幂等恢复。不能把当前重试称为断点续跑或宣称 Gateway 可横向扩展 |

## 内容实现对比

| 内容 | 已确认差异 | 应如何对齐 |
| --- | --- | --- |
| 事件 → 骨架 → 改编 → 剧本 | 三阶段与审核已实现。当前迁移明确把章节事件收敛为每章一条核心事件 | 保留已有每章一条规则；重要细节通过原文读取补充，为骨架/剧本记录来源章节，验收跨章因果、台词与集数覆盖 |
| 基础人物和场景造型 | 上游基础人物可带基础着装，只在明显换装/变身/形变时衍生。Rust 独立维护身份与 appearances，并要求分镜人物一律引用衍生 | 保留身份和造型分离的数据能力；改为可复用造型优先，仅必要变化创建新图。旧项目的中性底模不能直接作为正式服装入镜，必须核验已有成图是否符合本场造型 |
| 场景衍生 | 上游支持日/夜等时间变体；Rust `add_deriveAsset` 当前只允许人物，场景变化引导到分镜阶段 | 补同一空间的时间状态能力，复用现有场景一致性表/参考图；避免重复造两套场景关系。日夜状态与全新地点必须区分 |
| 资产提取 | 上游返回新资产和已有引用；Rust 增加 costume、年龄阶段和逐场 appearances，结构更丰富 | 保留新增结构；减少无必要的独立服装图片，完善已有人物/造型去重和场次绑定 |
| 润色与生图 | 上游接口查询 `type/intro`，但实际基础资产润色/生图 prompt 没用这两项；衍生批量生图会重新润色并更新 prompt | 不照搬遗漏与覆盖行为。当前未提交修复已把题材/简介传入资产润色和生图，并恢复衍生提示词编辑；后续验证最终发送文本尊重手改内容，完成入口一致性检查 |
| 分镜表 → 面板 | 上游按视频模式选择片段级纯文本或逐镜首帧，并使用画风/模型对应模板 | 对齐模板和字段语义；保留 Rust 的资产ID、参考顺序、姿态、时长、批次回滚检查。校验失败应定位具体行，不应无差别重写整集 |
| 监督审核 | 上游主要审核内容文档；Rust 分镜表写入后自动读取最新内容复审，并有机械校验 | 保留自动复审；将格式/引用错误和创作建议分开。审核绑定产出版本，内容改动后旧“通过”失效。文档审核不能冒充实际图片视觉验收 |
| 视频与成片 | 上游决策手册明确引导用户到视频面板生成/合成；Rust 已有视频提示词、轨道、导出及成片归档 | 对齐完整工作台操作；保留现有导出、归档和 Worker。Agent 自动生成视频属于另外的能力扩展，不能当作上游已有功能 |
| 古今混合 | 所查路径中没有专用穿越世界观机制；部分画风手册直接禁止另一时代物件 | 项目简介确定世界规则；场次确定时空；人物造型、道具保留各自年代；画风只负责审美。用户已明确的时代事实必须覆盖画风模板里的默认年代 |

## 不能原样复制的冲突

1. 上游生产决策 Skill 写“仅阶段4审核”，后文又要求阶段1和4审核；衍生分析在决策 Skill 中依赖导演预划，在执行 Skill 中却明确不读预划。先选定一致规则再接入。
2. Rust 初始内容同时留有旧生产顺序与“人物衍生优先”的覆盖段落；监督规则仍有“特殊光照走场景衍生”，而工具拒绝创建场景衍生。需要统一 Skill、工具和数据模型。
3. Rust 工具说明仍展示 `add_deriveAsset({assetsId,id,name,desc})`，实际处理要求 `appearanceId`。工具 schema、提示词示例与处理函数必须有同一份契约。
4. 上游读取了简介但没有把它用于基础资产 prompt；不能用“查询里有 intro”当作世界观已传递的证据。
5. 既有手册含带年代的禁止项，直接全量覆盖会重新引入古风与现代冲突。人工修改提示词、头像身份设定及用户自定义手册都应保留。

## 实施顺序与验收

### P0：主剧场的上下文、技能与规则一致性

1. 读取运行中的 Skill、手册、模型映射，与固定上游 commit 建立清单：来源、版本、项目适用范围、用户修改、当前消费者。
2. 实现共享上下文结构：项目题材/简介、选定美术与叙事手册、当前集/场、模型模式、资产ID和最新版本。接入资产提取、润色、生成、生产决策与执行阶段。
3. 修通技能目录与手册解析，按项目精确选取，执行 Agent 能实际加载对应内容；保留通用生产技法，避免加载其他画风的规则。
4. 统一各层工具 schema 与 Skill 调用示例；为创作内容设定明确优先顺序：用户当前明确修改 → 项目/剧本事实与已确认资产 → 选定画风技法 → 通用默认值。
5. 清理相互矛盾的阶段规则，阶段完成以实际保存的内容及必要媒体状态为依据。已有授权和项目配置直接使用，只询问真正缺少的创作选择。

验收：同一“古风画风 + 古今混合简介”的测试项目，现代404公寓保留电脑、冷白灯、冰雹、泡面桶；古代客栈保留古代结构；明确同框的古今元素并存；其他画风技能不出现在该项目执行上下文里。记录最终 prompt 可核查每项输入来源。

### P1：按需衍生、工作台反馈与恢复

1. 以“导演规划 → 按需衍生分析/生成 → 分镜表与审核 → 面板 → 生图”为默认逻辑，规划可先做，付费图片就绪只阻挡真正依赖它的媒体步骤；用户明确授权的步骤连续执行。
2. 同一人物、同一套造型跨场复用。仅变化时新增，允许现代/古装多个造型；已有身份底模、正式着装图与旧衍生关系继续兼容。
3. 支持同一场景日夜状态并保持空间参照；整合现有场景一致性能力。
4. 贯通子 Agent 进度和版本化产出；编辑保存后刷新工作区，重生成使用保存的人工 prompt。
5. 保存阶段输入版本、产出ID、生成任务ID与审核版本；重复点击/重试先查询产出和任务状态，避免再次付费生成已完成内容。

验收：同服装跨三场不重复生成；换古装时身份保持；只重试失败资产；断线重连能恢复进度；只改一镜不会覆盖其余镜头；人工 prompt 保存后实际发送内容可追踪。

### P2：内容质量回归与专题剧场

1. 用相同剧本、模型、尺寸和参考图分别跑基线与新链路，比较事实遗漏/新增、人物身份、服装、场景年代、分镜覆盖、调用次数与耗时。先用模拟模型验链路，再做限定范围真实供应商验证。
2. 增加“穿越剧场”入口或项目模板，复用主剧场；扩展时空设定、角色造型映射、穿越前后物件连续性。只有现有字段不足时才新增结构化字段。
3. 将文本审核与图片视觉验收区分展示，图片的身份/年代/物体正确性需要实际预览或独立视觉检查。

不按文件数量或同名API数量宣称“全面对齐”。完成标准是同一测试项目能走通：导入 → 事件 → 骨架 → 改编 → 剧本 → 资产/衍生 → 导演规划 → 分镜 → 视频 → 成片，且能编辑、取消、重试、刷新恢复。

## 数据和交付约束

- 先修 P0，再做 P1，专题剧场放在 P2；实施不批量覆盖数据库或改写旧作品。
- 若修改 Skill 基线或新增字段，追加编号迁移，不改已应用迁移；按 AGENTS.md 运行空库迁移测试、更新快照和迁移断言。
- 保留用户自定义 Skill/手册/提示词；升级需要内容版本或原始哈希匹配，避免无条件 upsert 覆盖。
- 保留单 Gateway 约束，媒体容量通过 Worker 扩展。
- 截至第二批没有运行真实 AI 对比、重新生成用户图片或部署尚未提交的修复。最新验证范围见“当前实施进度”；仅模拟调用与局部浏览器交互通过，不代表真实图片质量或整个制作流程已对齐。
